# 实例部署改善 — v2 投影归属与链接对账

立案日期：2026-09-21

## 状态与范围

本文件按用户要求记录已选定的 v2 设计方向与实施边界，尚未实施或通过运行验收。完整记录设计细节是本次用户明确要求；未定项须在实现时闭合，不能当成已完成的行为。

v2 是对当前机制的改善：保持 import 实体复制、persist 符号链接及目录接管、package 投影，补充 build 内部署归属记录，完善来源转换，并把真实对象的规划／实施与最后的符号链接 diff merge 重新分开。

[v1 设计记录](todo-2026-09-21-live-projection-and-deployment-rules.md)保留为比较依据。v2 不恢复 live，不引入 persist/live 双向副本同步，不采用硬链接，也不把 persist 缩减为 build 内文件的 reset 保护声明。v1 的新增整合包源规则、import `.keep` 默认生成、live 目录投影和包链接进入 live 的设想不进入本方案。

## 目的与不变契约

- 整合包源（`import/`）是独立的源数据，跨重置保留；游戏不能自动写回它。工作区仍允许作者显式同步内容到 import。
- 本地保留（`persist/`）是用户独立存放的高优先级可写内容。它提供用户覆盖、直接写入和必要的回迁能力，跨重置保留是这些能力的结果。
- 运行目录（`build/`）承载构建产物及运行状态。用户可以丢弃构建产物；其中未放入 persist 的存档、截图和配置仍可能永久丢失。清单不改变这一数据边界。
- import 的已有工作副本在普通部署中不随源内容变化自动覆盖；缺失则补齐，手动修改源后的内容同步仍由工作区触发。
- 作者可以直接通过文件资源管理器、编辑器、Git 或脚本维护 import。删除跟随不依赖工作区按钮或持续运行的文件监听。
- Trident 核心实现规则，CLI 和桌面共享结果。保留当前整合包更新的暂存／回滚、Patch 层边界和其他已成立的能力。

## 现有机制核对

核对入口为 `submodules/Trident.Net/src/TridentCore.Core/Engines/Deploying/DeploymentPlanner.cs`。实现时再以届时源码为准。

当前规划器先收集 package、import、persist 候选，再按优先级和路径关系筛选，并非完全没有“先仲裁后投影”。

| 情况 | 当前行为 | v2 方向 |
| --- | --- | --- |
| 相同目标文件路径 | persist > import > package | 保留 |
| persist 目录内存在 `.keep` | 整个目录符号链接到 build | 保留 |
| persist 目录投影覆盖低优先级子项 | 下方 import/package 候选被遮蔽 | 保留该目录接管语义 |
| 普通 persist 子目录没有 `.keep` | 递归收集文件，不自动整体接管目录 | 保留 |
| import 文件 | 在 build 中复制实体文件，只补缺失 | 保留 |
| import 目录中有 `.keep` 文件 | 不触发目录投影，按普通文件收集与复制 | 保留，不新增标记生成或解释 |
| 文件与目录祖先／后代不能共存 | 部分情况报冲突 | 核对完整边界，不宣称所有类型转换已自动解决 |
| persist 投影处出现普通文件／目录 | 规划回迁后建立链接 | 保留自愈，但新增对旧 import 归属的区分 |
| 源目录或内部包含符号链接 | 当前扫描拒绝 | 此次不无意放宽该约束 |
| persist 根放置 `.keep` | 当前拒绝整个根目录投影 | 保留 |

### import 的 .keep 口径

“import 不允许 `.keep`”在本方案中准确表示：**import 不提供 `.keep` 的目录投影语义**。当前代码并没有禁止磁盘中出现这个名字的文件；它会作为普通文件复制。v2 沿用这一行为，不新增仅因文件名而拒绝整合包的校验。

import 已经复制为实体文件，无须借助整体目录链接解决其资源包内部符号链接问题。因此安装、导入、整合包更新均不为 import 自动生成 `.keep`。

persist 的 `.keep` 继续承载整个可写目录，例如 `persist/saves/.keep` 让游戏在目录投影下直接创建和修改 persist 中的存档；不会增加另一份 live 存档副本。

v1 中“import 目录链接与 persist 内部文件链接重叠”的问题不出现在本布局：import 没有目录链接。但 persist 单文件投影本身仍是符号链接；本方案不声称消除所有人为覆盖场景中的资源枚举限制，也不为此引入新的文件链接技术。

### 仲裁与应用仍须区分

当前候选树能够表达遮蔽，不代表落盘转换已正确。

特别是新增 persist 内容时，build 中可能仍有上次的 import 普通副本。旧 import 归属可以证明该副本应退出管理，persist 内容必须胜出，不能把 build 副本回迁后覆盖用户新加入的 persist 文件。

persist `.keep` 目录接管时逐项处理普通内容：persist 目标缺失则把 build 内容迁入 persist；双方存在同路径普通文件时，已知旧 import 副本由 persist 胜出，其他无法证明来源关系的双副本明确报冲突。不能替用户删除或覆盖未知的任何一份。

## build 内部署归属记录

### import 归属

`trident.import.json` 记录**上一次已应用、实际生效的 import 工作副本相对路径**，不是 import 目录的原始全量文件列表，也不是某次操作中仅发生了 Copy 的文件列表。

```json
{
  "version": 1,
  "files": [
    "mods/a.jar",
    "config/example.json"
  ]
}
```

- 被 persist 同名文件或目录投影遮蔽的 import 路径不进入清单。
- 已存在且仍被认作 import 工作副本的普通文件进入清单，即使本次没有发生复制。
- package、persist 链接和未托管的 build 内容不进入清单。
- import 归属绑定路径，不记录内容字节或修改时间；普通部署不根据时间自动同步 import 与工作副本。

### persist 单文件投影状态

`trident.persist.json` 只记录上次实际生效的 **persist 单文件投影**及当时 persist 源文件的修改时间。它用于区分两种外观相同的状态：游戏以 Delete-Create 替换了原有链接，或用户后来新增 persist 文件试图接管既有 build 普通文件。

- 上次是 persist 单文件投影、build 现为普通文件且 persist 修改时间未变：认作 Delete-Create 写入，回迁 build 后重建链接。
- 上次是 persist 单文件投影、build 现为普通文件且 persist 修改时间已变：persist 源在期间发生修改，由 persist 胜出后重建链接。
- 没有旧 persist 单文件记录且双方都有普通文件：来源关系未知，报冲突。
- 上次是 import、本次由 persist 文件接管：persist 胜出，不触发回迁。
- 修改时间是相对上次记录的变化依据，不拿 build 与 persist 的时间直接比较；记录本次实体处理完成后的 persist 状态。

persist `.keep` 目录不记录内部全量文件时间，也不维护 `persistDirectories` 清单，避免大型存档和截图目录产生庞大元数据。目录链接被普通目录替换或首次接管时使用统一的逐项规则：目标缺失则迁入；已知旧 import 与 persist 冲突时 persist 胜出；其他内容不同的双副本报冲突。

### 生命周期与存储约束

归属记录描述 build 内部署结果，与 build 同生共灭。整个 build 被重置或删除时记录一起消失；下一次部署从当前来源建立新基线。persist 仍物理独立于 build，记录丢失不意味着 persist 内容失去保护。

- 使用规范化的 build 相对路径、稳定排序和平台匹配的路径比较规则。
- 读取时验证格式版本、路径范围、重复与非法条目；禁止绝对路径和越界路径。
- 两份正式记录及其提交用临时路径是构建元数据保留位置，import、persist 和 package 同名输出不能覆盖。
- build 根、记录文件或路径祖先若存在非预期链接，不能沿链接读取或写入外部目标。
- 缺失 import 记录表示首次基线：`OldImport` 为空，不做历史差异删除，只在部署成功后产出当前记录。
- 损坏或不支持版本的记录应明确报告，不能静默当空集合执行破坏性清理。

## 差异与删除跟随

记旧有效 import 路径集合为 `OldImport`，本次仲裁胜出的 import 路径集合为 `NewImport`：

```text
RetiredImport = OldImport − NewImport
```

这是退出 import 管理的集合，既包括源删除，也包括源仍存在但被 persist 接管。

| 本次路径归属 | 处理 |
| --- | --- |
| 没有来源接替 | 删除经确认仍是旧 import 的 build 普通副本 |
| persist 文件接管 | 移除旧 import 副本占位并应用 persist 投影，不将旧内容回迁覆盖 persist |
| persist 目录接管该路径 | 纳入目录接管的整体计划，逐项处理旧 import 占位，避免沿目录链接删除持久目标 |
| package 接替 | 移除旧 import 副本后应用 package 投影 |
| 路径已不存在 | 仅退出清单，无需删除实体 |
| 已变为链接或出现不符合预期的结构 | 按链接对账或明确冲突处理，不按普通文件盲删 |

所有判断以最终仲裁结果和实际路径结构为准。`persist/同路径文件存在` 不是唯一判据，祖先的 `.keep` 目录投影也可以接管该路径。

即使用户或游戏修改过旧 import 工作副本，只要它仍按该路径归 import 管理，源删除后仍跟随清理。内容变化或 Delete-Create 同名重建不会自动解除该路径的归属。需要保留的内容应交由 persist 接管。

从未进入清单的 build 普通文件，不因 import 中不存在同名路径而删除。目录清理只移除已确认可删除的空目录，不递归带走未知子项。普通文件和目录类型发生变化时，使用明确的冲突／转换规则，不能让文件删除意图扩大为整目录删除。

## 来源切换与回迁

本次仲裁和上次归属要共同决定操作，不能只看到 build 普通文件就回迁。

| 上次归属及当前结构 | 本次有效来源 | 语义 |
| --- | --- | --- |
| import 普通副本 | persist 文件 | persist 胜出，旧 import 副本不回迁 |
| persist 单文件投影被替换，persist mtime 未变 | persist 文件 | 回迁 build，再建立链接 |
| persist 单文件投影被替换，persist mtime 已变 | persist 文件 | persist 胜出，再建立链接 |
| 无历史归属且 build/persist 都有普通文件 | persist 文件或目录 | 无法判断用户是否仍需 build 副本，报冲突 |
| import 普通副本 | import | 保留已有内容，只补缺失 |
| 已有符号链接 | 任意最终来源 | 不作为真实对象冲突，由收尾链接对账统一处理 |

旧记录描述上一次成功部署的归属和 persist 源状态，不是当前文件结构的绝对证明。实体处理仍须检查实际路径结构，不能沿符号链接删除目标，也不能仅凭路径记录授权覆盖 persist 数据。

persist 目录中真正的游戏写入继续直接落在 persist。普通目录需要接管时只迁移目标不存在的内容；同路径双副本除已知旧 import 外均报冲突。同一文件不能既安排删除又安排回迁。

## 真实对象规划、执行与链接收尾

### DeploymentPlanner

DeploymentPlanner 保持无网络、无文件系统写入，并且只处理真实对象：

1. 读取并验证旧归属记录。
2. 扫描 package、import、persist 来源并完成最终路径仲裁。
3. 计算退出 import 管理的路径、persist 回迁／冲突以及需要补齐的真实文件。
4. 返回下载和实体文件操作、最终投影映射，以及成功后应提交的归属记录。

Planner 不枚举现存符号链接、不比较链接目标，也不输出 `RemoveLink` / `Link`。符号链接是可丢弃的部署投影，不参与真实对象的来源判断。

### 执行与符号链接 diff merge

部署严格按单向阶段向下执行：

```text
读取与验证归属记录
扫描并仲裁来源
规划真实对象
下载并应用删除、回迁、复制等实体操作
根据最终投影映射独立执行符号链接 diff merge
提交新的归属记录
```

实体操作若在目标或祖先遇到符号链接，只删除挡路的链接本身后继续，绝不沿链接写入目标。这是实体操作的安全落盘方式，不代替最后的全树链接对账。

部署收尾恢复并改善独立的 SymlinkPhotos 职责：消费前面已经确定的完整最终链接集合，对 build 中现有链接执行 diff merge——正确链接保留，错误链接替换，多余链接删除，缺失链接补齐。链接需求只来自本次仲裁结果，不从磁盘上是否还存在旧链接反推；用户删除全部链接后再次部署也能完整恢复。

`DeploymentPlan` 携带实体操作、最终投影映射和计划完成后的归属结果。执行阶段不能重新扫描来源生成另一份结果。规划器不提前修改文件，也不通过已经加入计划的操作反推虚拟文件状态。

### 失败后的幂等收敛

本方案不引入跨整个部署的文件系统事务或回滚日志。正式归属记录在实体操作和链接对账全部成功后才以同目录临时文件替换提交；执行操作必须允许失败后重新规划并收敛：

- 已删除的旧副本再次删除视为完成。
- 已完成的复制、回迁和正确链接不重复破坏。
- 已由 persist 接管的路径不得因旧 import 记录沿链接删除持久目标。
- 部分新 import 副本在提交前失败且来源随后消失时可以保守遗留为未托管内容，不能猜测后删除。
- 无法根据旧记录和实际结构证明安全的双副本始终报冲突。

## 生命周期和周边机制

### 重置与整合包更新

重置继续清除 build 和部署锁，归属记录随 build 一起清除；import、persist 按既有契约保留，不增加 reset 保护名单。

整合包更新继续准备新源、备份旧工作副本并支持失败回滚。旧 import 记录参与旧副本识别，避免作者已删源的工作副本被遗漏。更新提交成功后删除旧归属记录，由下一次部署建立新基线；更新失败并回滚时保留旧记录。

### 工作区与快照

工作区仍比较 import 与 build 中的工作副本。清单提供源已删除后仍可识别的旧投影范围；被 persist 遮蔽的路径不能误列成 import 工作副本并允许错误同步。

当前快照按仍存在的 import 枚举工作副本。新快照需保存有效 import 工作副本及对应归属记录；还原时先读取旧记录界定当前受管范围，文件还原完成后再提交快照携带的记录，不能将还原前的新归属与还原后的旧内容混用。

本方案不改回 live 路径。历史快照和无清单实例仍需兼容核对，不因为目录布局没变就跳过恢复路径检查。

### 导入导出与作者工作流

整合包导入仍写 import；导出仍读取 import 及已定义的其他可分发内容。build 内部署归属记录不随整合包分发，也不变成作者维护的文件。

作者可在软件关闭时修改、删除 import，或切换 Git 分支。下一次部署通过持久的已应用清单识别变化。文件监听可以刷新界面，但不承担唯一的删除历史记录。

## 首次部署与存量边界

- 没有 import 记录时令 `OldImport` 为空，不执行历史差异删除；正常完成本次仲裁与实体补齐后产出当前基线。
- 有效 import 普通副本可以按当前只补缺失机制继续使用，不要求为建立记录重置实例。
- 没有 persist 单文件记录时，不猜测 build 普通文件是旧链接的 Delete-Create 结果；双方已有实体则报冲突。
- build 被完整删除时，记录缺失是正常的新构建状态。
- 单独损坏／删除记录时不自动扩大删除或覆盖范围。
- 旧链接统一交给独立的收尾 diff merge；本次不增加 live 迁移。

## 实施范围与验收

核心范围是现有规划／执行流程、清单读写、来源转换和相关生命周期适配。v1 中的规则 UI 重做、新的整合包源规则和默认 `.keep` 生成不属于此 v2。现有包规则能力保留。

用真实实例验证，至少包括：

- import 新增、内容修改保持手动同步、删除文件及含多个文件的目录。
- 删除源后清理对应旧副本，保留同目录中的未托管文件。
- persist 同名文件接管、persist `.keep` 父目录接管，且新 persist 内容不被旧 import 副本覆盖。
- persist 单文件 Open-Overwrite、Delete-Create、persist 源同时修改，以及无历史双副本冲突。
- persist 目录接管时目标缺失的回迁、旧 import 冲突由 persist 胜出、未知双副本报错。
- import 删除后 package 同路径接替，以及被 persist 目录遮蔽的候选。
- import 中 `.keep` 仅按普通文件复制，persist 中 `.keep` 仍触发目录投影。
- 用户删除全部符号链接后的完整重建、链接目标变化和多余链接清理。
- 目标或祖先链接、文件／目录类型冲突、归属记录保留路径冲突。
- 无记录首次部署、损坏记录、部分应用失败与幂等重试、提交失败。
- 整合包更新成功／失败回滚、快照还原、reset 后重新部署。
- CLI 与桌面操作一致，作者通过文件资源管理器和 Git 修改源仍能正确工作。

只做构建不能证明运行行为。遵守仓库不新增功能测试项目、不运行格式化工具的约定。
