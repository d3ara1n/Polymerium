# 历史兼容代码退出计划

## 背景

Trident 的实例数据会跨应用版本长期留在磁盘上，也会通过整合包与本地快照再次进入当前版本。格式演进时保留的兼容读取分支，容易在过渡结束后继续占据正式模型与运行路径。仅写“迁移完成后移除”不足以界定兼容期，也不能保证后续版本真正完成清理。

本计划作为长期待办，推动历史兼容逐项退出，直至当前范围内的遗留项全部清理。长期的是退出工作，不是无限延长每个兼容分支的寿命。

## 要做什么

清理为 Trident 自身旧数据形态保留的临时兼容，当前关注以下范围：

- Java 需求由单个大版本改为兼容集合后保留的旧 Patch 文档、旧操作目标与旧锁字段读取。
- 包引用字段由旧 `purl` 名称转向 Pref 后，在实例配置与锁定数据中保留的旧字段入口。

已有的独立任务与期限：

- Java 标量兼容：[POLY-167](https://d3ara1n.atlassian.net/browse/POLY-167)，约定在 v1.14.0 移除。
- Purl 兼容：[POLY-123](https://d3ara1n.atlassian.net/browse/POLY-123)，保留至 v1.16.0，届时按该任务核对旧字段、旧格式解析及相关类型约束。

各项退出取舍以对应任务为准。本计划不重新开启兼容期，也不因纳入长期工作而延期。对不承载有效业务含义的缓存占位结构，可直接清理，不必为允许失效重建的锁文件另设兼容期。

后续确需新增自身历史格式兼容时，也应有明确的保留理由、退出目标和可关闭的跟踪任务，避免用长期计划替代单项期限。

## 想要的效果

每个历史兼容项都能明确说明：它保护哪一类旧数据、当前是否仍会产生这种数据、保留到什么时候、移除后对未升级数据有什么影响，以及是否接受停止支持。

兼容项退出后，正式模型只表达当前支持的数据形态，临时读取分支与过期说明一并清理。完成情况以实际支持边界和代码状态为准，不能仅以时间经过或一次构建成功判断。

## 注意事项

外部格式导入与目录迁移是持续支持的产品功能，不属于等待删除的自身历史兼容。源格式的语义应在转换边界解释，Trident 原生 Patch 保持独立语义；不能为清理历史兼容而删除仍受支持的外部格式转换。

占位符解析、缓存失效与重建、缺失 native 文件恢复也是正式机制，不因能处理旧实例就列为临时兼容。

Patch 文档、实例配置是声明来源，锁定数据则承载已解析的结果。两者的退出影响不同：不能用“缓存可以重建”推导出源声明可以删除；重建锁还可能重新解析浮动包引用，必须准确说明版本变化的边界。

未启用的 Patch、长期未启动的实例、旧整合包和快照恢复都可能重新带回旧格式。读时转换并不等于原文件已经更新；兼容分支的退出必须明确如何看待这些尚未更新的数据，不能假定它们会自动消失。

本文保留退出工作的意图，具体实施前重新核对当时的代码与支持约定，不将当前文件位置或内部结构固化为长期方案。
