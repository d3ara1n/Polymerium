# Trident CLI 服务端部署与启动

立案日期：2026-10-25

## 背景

整合包作者希望从已有实例交付可运行的服务端，让服主按实例声明下载所需内容并启动游戏。最初的使用场景是发布到 CurseForge 的服务端包，但独立下载启动器涉及仓库认证、加载器安装和运行环境，暂不将其作为 Polymerium 的导出功能推进。

后续由 Trident CLI 承担服务端部署与启动，接受服主安装并配置 Trident 的使用前提。期望入口形如 `trident server up --instance test`，让已有实例成为服务端的声明来源；具体命令契约在实施时结合当时的 CLI 确定。

纯下载是必须保留的交付能力。携带获得许可的模组文件可以是另一种分发方式，但不能替代纯下载：作者只分发实例声明和获准分发的配置，由服主从允许的来源获取模组，可以避免由整合包作者重新分发受限模组文件。

## 做什么

- 让 Trident CLI 根据指定实例准备服务端所需的 Minecraft 本体、模组加载器、模组和配置，并启动服务端。
- 支持只交付实例声明与配置、在接收端下载所需文件的使用方式，不要求发布者提供自包含的模组归档。
- 允许作者明确服务端包含和排除哪些包与文件，并表达服务端专用配置及额外包，避免将客户端实例内容原样用于专用服务端。
- 明确仓库认证、必要文件无法自动下载、Java 运行环境和 Minecraft EULA 接受等前提，让服主知道哪些条件尚未满足。
- 本计划聚焦 Trident Core 与 CLI 的服务端能力；Polymerium 界面、独立即开即用的发行包和 CurseForge 上传集成留待后续需求。

## 期望效果

- 服主获得实例声明和配置后，完成必要的仓库与运行环境配置，即可通过一个入口完成部署并启动服务端，不必逐个下载模组或手动拼装加载器启动命令。
- 接收端得到与发布者指定版本一致的服务端，不因部署时间不同而悄然选择新的包版本。
- 客户端专用内容及兼容性未知的包有明确的处理结果，必要依赖缺失或受限下载不会被静默忽略后继续启动。
- 服务端运行与客户端使用不会互相覆盖数据；重复启动保留世界、服主配置和其他运行数据。
- 验收使用真实整合包，在隔离目录完成首次部署、实际启动、客户端加入及再次启动，不能仅以成功生成目录或编译通过证明可用。

## 调研注意事项

- Minecraft 本体再分发、模组文件再分发许可、资源仓库的自动下载权限是不同约束。纯下载避免交付模组副本，但不绕过仓库认证或作者关闭第三方下载的限制。
- CurseForge API 需要 API key，官方也已公布 CDN 下载的 API key 要求。下载凭据的获取与使用边界需要在实施时重新核实，不能把发布者的私有凭据随实例交付，也不能将可拼接的 CDN 地址视为允许自动下载的依据。
- 已查阅的 ServerStarter 示例配置使用 `curseForgeApiKey`，支持从 `CURSE_FORGE_API_KEY` 环境变量读取；这不能证明分发的启动器自带可供所有人使用的 key，也不能据其流行程度推断它仍适用当前下载规则。
- Minecraft、模组加载器和模组侧别的服务端支持范围，需要在实施时对照当时的 Trident 能力及真实整合包确认；未知兼容性不能当作已经验证的支持。
- CurseForge 官方教程允许将模组与配置目录打包，并要求服务端包作为对应主整合包版本的附加文件上传。这支持常规服务端 ZIP 的发布方式，不等于任意下载器或 Trident 实例声明都已获平台认可。
