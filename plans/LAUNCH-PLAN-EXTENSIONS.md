# 可组合启动计划扩展

## 背景

当前实例已经能够使用一个规范化的外挂启动计划参与部署和启动。该计划与 Profile 分离，适合承载由外部整合包导入的启动层意图；部署锁只保存计算结果，不承担持久化职责。

下一阶段需要把这个单一外挂扩展为可组合的启动计划目录体系，使外部来源、规范化计划和用户自定义计划彼此解耦。外部来源文件只用于导入和转换，运行时不应依赖来源格式或来源文件是否存在。

## 目标

- 让 `launch/` 成为完整、稳定、来源无关的启动计划空间。
- 支持多个规范化计划目录共同作用，并通过目录命名确定叠加顺序和优先级。
- 将导入得到的来源内容转换为规范化计划后再参与运行，后续导出也从规范化计划生成目标格式，而不是回放保存的来源文件。
- 为用户保留独立的计划目录，用于维护自己的启动意图，不与导入来源混淆。
- 让计划叠加具备清晰、可预测、可诊断的覆盖语义。
- 在不改变 Profile 基础实例配置职责的前提下，提供完整的启动层定制能力。

## 预期效果

- 删除或替换某个来源目录不会让运行时继续隐式依赖原始来源文件。
- 同一个实例可以同时承载导入计划和用户计划，且优先级稳定可解释。
- 从实例导出外部组件格式时，结果反映当前规范化计划的最终内容。
- 用户可以只修改自己的计划目录而不改变导入来源的原始语义。
- 启动计划、部署快照、Profile 和实例文件的生命周期边界清晰一致。

## 已知约束

- 计划文件只表达启动层行为；包声明和部署规则仍由 Profile 及其既有规则体系负责。
- 导入来源目录与用户维护目录必须在语义上区分，不能用“是否被修改”推断所有权。
- 目录优先级需要具备确定性，并且能够覆盖低优先级计划的同类声明。
- 来源格式只在导入和导出边界出现，运行时消费统一的 Polymerium 原生计划。
- 本阶段不预设具体 UI；计划目录应先具备稳定的文件规范和诊断语义。
