# 可组合启动计划扩展

## 背景

当前实例已经能够使用一个规范化的外挂启动计划参与部署和启动。该计划与 Profile 分离，适合承载由外部整合包导入的启动层意图；部署锁只保存计算结果，不承担持久化职责。

下一阶段需要把单一外挂计划扩展为来源托管计划与用户计划并存的启动计划空间。MMC pack 可能包含多个有顺序的 patch，因此不能把整个来源压缩成单个计划文件；来源 patch 需要在导入后分别转换为原生计划，同时保留其顺序和目标格式身份所需的信息。

## 目标

- 让 `launch/` 成为来源无关的原生启动计划空间。
- 保留 `launch/source/` 作为唯一由 MMC pack 导入流程托管的目录。
- 支持 `source/` 中多个按文件名排序的原生计划文件，并按 MMC patch 顺序生成它们。
- 支持 `launch/` 根目录下由用户自行维护的计划文件，并在来源计划之后叠加。
- 使导入得到的 MMC patch 转换为原生计划后再参与运行，运行时不依赖 MMC 原始文件。
- 从原生计划逐层生成 MMC patch，尽量保持来源 patch 边界、顺序和身份。
- 支持原生计划中的相对本地文件引用，并以所属计划文件所在目录作为解析基准。
- 让被禁用的计划文件可以通过点号前缀保留在文件系统中而不参与运行。
- 为转换与导出提供独立的错误、警告和结果诊断，不将诊断写入计划文件或 Profile。

## 预期效果

- MMC pack 中的多个 patch 不会因导入而丢失顺序或被强行合并。
- 更新整合包时只替换 `launch/source/`，用户根目录下的计划文件不受影响。
- 用户可以通过新增、重命名或点号前缀控制自己的计划层，而不需要伪造来源元数据。
- 来源计划中的本地库文件相对于其计划文件解析，且其内容变化会使部署快照失效。
- 从 Polymerium 实例导出 MMC pack 时，每个有效计划层都可以生成独立 patch；无法表达的内容通过诊断明确提示。

## 已知约束

- `source` 是保留目录名，只扫描该目录的直接文件；`launch/` 根目录只扫描直接的用户计划文件，不递归发现其他目录。
- 计划文件使用统一的 Polymerium 原生 schema；MMC `patches/<uid>.json` 只在导入和导出边界出现。
- 文件名顺序使用跨平台固定的逐字符 Ordinal 比较，数字前缀不转换为整数；来源文件名中的数字前缀之后保留 MMC UID 候选。
- 以 `.` 开头的计划文件被忽略，不参与解析、叠加、hash 或导出。
- 来源计划的相对文件引用必须留在受管理的 `launch/` 范围内；用户计划可以使用绝对本地路径。
- 用户计划本身不随整合包导出；Trident 原生导出只携带托管的 `source/` 层。
- LaunchPlan operation 只表达启动行为；MMC 组件依赖、冲突和其他组件图元数据不进入原生计划。
