# 联邦整合包搜索（curseforge + modrinth）

## 背景

市场页（整合包入口）目前必须先在仓库选择器里二选一（curseforge / modrinth），一次搜索只打一家，用户感知到的"覆盖面不全"即来源于此。曾评估把搜索（乃至下载安装）切到第三方聚合站的 API，调研后全部否决：

- **modpackindex.com**：纯元数据目录。API 免 key（3600 req/h），但无版本列表、无文件、无下载 URL；搜索参数实测只有 `name` 过滤生效；API 于 2026-06 才重写发布，无 SLA。只能当目录用，当不了搜索后端。
- **moddex.gg**：CF+MR 的评论/评分聚合层。设计上从不分发文件（下载按钮全部跳回上游，自述获两平台许可），"替换下载安装"客观上不成立；其 API 需注册账号签发个人 token、文档在登录墙后、ToS 限定"personal and non-commercial use"且可随时任意吊销、单人运营无法律实体——对分发到最终用户手里的启动器不可用。

结论：跨仓库统一搜索自建，不引入第三方中间层；下载安装链路维持现状（按 label 路由到对应仓库解析直链）。

## 做什么

在 Core 层为仓库搜索提供联邦能力：一次查询并发打到 curseforge 与 modrinth 两个仓库，结果合并为单一分页流。市场页仓库选择器增加"聚合"条目并设为默认；favorite 等本地伪仓库不参与联邦。筛选器（loader/version）取两源状态的并集。

期望的分页形态是**按名次交错**（合并第 k 页 = 两源各自第 k 页交错），理由：请求量与单源搜索持平、延迟取两源较慢者、对可随意 set 的 PageIndex 契约是纯函数映射；两家 relevance 不可比，交错即联邦搜索的标准诚实合并。按下载量双指针归并（强制两源 sort=downloads）可作为显式排序选项的后续形态，不作默认。

## 想要什么效果

- 搜索一次覆盖两家，无需切标签；
- 列表层去重：同一项目（跨平台同 slug）只出一张卡，first-wins（流式分页下页一旦产出即冻结，无法也不应反悔换代表）；
- 平台选择不丢失，但**下沉到详情层**（v2，独立于联邦搜索可先行/后行）：打开卡片详情时用手里 slug 去另一家平台反查（CF 的 slug 搜索参数、MR 的 id-or-slug 项目端点均为现成能力），详情视图并列展示两家的版本列表，安装按用户所选版本走各自平台路由。列表管发现（去重），详情管来源（保真）。

## 调研所得的注意事项

- **slug 去重是机会性匹配，不是保证**：CF/MR 是独立命名空间，无跨平台一致性义务（CF 撞名自动加后缀，MR slug 基本不可改）；但 slug 多由项目名派生，跨平台发布的头部项目同名率高，恰好覆盖去重最起作用的区域。slug 不一致的跨平台同项目会漏检，残留形态是"同项目两张卡、各带平台徽标"，可接受，不做名字兜底匹配（同名异物的误报比漏报更有害）。
- **名次不对称是常态**：同一项目可能 CF 第 1、MR 沉底。first-wins 意味着热门查询下合并卡常为 CF 代表——列表层这是正确行为（搜索的语义是找到项目），平台选择由详情层联邦兜底，不要试图在列表层做迟到换卡（用户眼皮底下卡片变脸比重复更糟）。
- **`Exhibit` 现不携带 slug**：CF/MR 搜索响应里都有 slug 字段但未映射到 Exhibit；`Namespace` 在两家搜索结果里均为 null，且参与收藏身份三元组 (label, ns, pid)，不要挪用它承载 slug。
- **分页契约**：`IPaginationHandle.PageIndex` 可随意 set 后 Fetch；UI 侧无限滚动按页顺序推进。交错方案天然满足；若引入去重状态（seen-set），需约定 PageIndex 回跳时重置状态，且 seen-set 应有界（深滚允许漏检）。
- **失败语义**：联邦搜索中单源失败应降级（剔除该源继续出结果）而非整体失败；单源耗尽后该页全给幸存源；TotalCount 为两源之和（含重复的上界），无限滚动以空页终止，不依赖其精确。
