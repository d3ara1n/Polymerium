# 应用内用户反馈渠道

## 背景

- 现有反馈入口只有应用菜单里的"反馈"，直接跳转 GitHub——对 Minecraft 玩家（尤其 Mirror酱 分发的国内用户）门槛过高，实际只能听到技术型用户的声音。
- 崩溃/异常已由 Sentry 被动收集，缺的是"不崩溃但体验差"的痛点报告、功能请求和纯讨论。
- 期望用户不需要任何账号、甚至匿名，就能提交 bug 反馈、功能请求或一般讨论。
- 曾考虑 QQ 群 / Discord 等社区即时渠道，但当前用户量小，暂缓——待用户规模起来后再作为补充渠道加入。

## 做什么

在应用内提供一个低门槛反馈界面，走 Sentry User Feedback 提交，覆盖 bug 反馈、功能建议、一般讨论三类。应用菜单现有的"反馈"入口改为打开该界面。QQ / Discord 渠道本期不做。

## 想要什么效果

- 用户零账号、低摩擦提交；愿意留联系方式者可选填，便于回复。
- 反馈进入 Sentry 面板，与崩溃报告同处一地，统一分拣；可 actionable 的转录到 GitHub/Jira 跟进。

## 调研所得的注意事项

- Sentry User Feedback 所有套餐免费包含，不需要付费；不消耗 error 配额，但随反馈附带的截图等附件计入 attachments 配额（基础 1GB）。
- sentry-dotnet 提供 `SentrySdk.CaptureFeedback`（替代已废弃的 `CaptureUserFeedback`），可独立于错误事件发送，返回 `SentryId` 并可通过 out 参数确认提交结果。
- 邮箱格式非法时 Sentry 服务端会静默丢弃该反馈——客户端需自行校验。
- 滥用风险：Sentry 刻意不对 feedback 做配额丢弃，DSN 内嵌于客户端属公开信息，理论上可被脚本刷量——实施时需考虑客户端侧节流（频率/长度限制）。
- 黑洞风险：用户提交后期待回音——界面需明确"如需回复请留联系方式"，并建立反馈分拣纪律，避免收了不看的观感比没有渠道更差。
