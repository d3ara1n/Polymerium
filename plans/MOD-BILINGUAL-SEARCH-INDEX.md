# 模组双语本地搜索索引计划

> 状态：构想，未实施。为集市浏览/搜索增加"本地聚合搜索 + 中文别名索引"，源自 GitHub issue #80；实施时对照当下真实代码临场决定 HOW，不回写本文件。

## 背景

- GitHub issue #80（d3ara1n/Polymerium）请求为模组/资源包/数据包/整合包添加中文翻译，建议集成 MC百科（mcmod.cn）数据源。
- 深挖后定位修正：**核心需求不是翻译，是"本地聚合搜索"**——中文/英文混合搜索都能命中模组，结果可跳转 CurseForge/Modrinth/GitHub，把搜索从"每次打远程 API"变成本地毫秒级查询。
- 翻译只是附属品且"没法直接翻译"：大众只接受口口相传的社区译名（通常是质量差但广泛使用的那个），LLM/机翻译名用户不认；唯一可靠的中文名来源是社区人工数据。
- 目标用户以中文为主，集市浏览目前依赖 Modrinth/CurseForge 在线 API，无中文支持、无本地搜索。

## 做什么

- 建立统一实体索引：把同一模组的 Modrinth/CurseForge（及可能的 GitHub/mcmod）条目关联为一个实体，实体承载中文名（社区译名）、别名、简介原文、可选翻译、各平台链接。
- 双轨搜索：本地索引优先（毫秒级、中英别名命中、离线可用），未命中透传远程官方 API 兜底——**未索引模组不丢失搜索能力**，只是没有增强（中文名/翻译）。
- 按需收录闭环：远程兜底命中"索引外模组"时，用户可请求收录/翻译（或匿名自动上报），服务端拉元数据建条目、跑翻译流水线，随 db 定期发布进入本地索引——索引随真实使用持续生长。
- 模组发现三路并进：冷启动种子导入 + Modrinth 主动轮询（官方 API 可全量）+ CurseForge 热度/用户请求（官方 API 无法全量）。
- 关联保守：文件 hash 匹配优先（最强信号），名称+作者完全一致次之，模糊匹配只出候选不自动合并——关联错了比不关联更糟。

## 想要什么效果

- 集市搜索本地化：中文别名（如"拔刀剑"→SlashBlade）、中英混搜、毫秒响应、离线可用。
- 索引随用户使用生长，冷启动靠种子数据，最终覆盖用户真实需求；用户搜索/请求过的模组最终都进入索引并带中文名。
- 搜索能力全程不中断：未收录模组走远程兜底照样能搜到、能跳转。
- 关联准确优先，宁可单平台独立收录也不把错误的中文名/翻译套到别的模组上。

## 调研所得（注意事项）

- **mcmod.cn 无公开 API、有反爬、数据版权归站方**：不能做运行时数据源，只能做一次性离线词典导入（约 2.4 万条中文名，是现成"社区译名"来源）。
- **mcmod 条目简介 ≠ 官方 description 的翻译**：是百科编辑另写的文本，"用 mcmod 给双平台补翻译"在语义上不成立，只能"补一份平行中文介绍"。
- **CurseForge API 无法全量枚举**（search 上限 index+pageSize≤10000）；**Modrinth API 可全量遍历**（limit+offset 无上限）——决定两边发现策略不同。
- **XMCL 已验证整套链路**（社区 CSV + sqlite 发布 + 客户端拉取），但其 i18n 仓库与 minecraft-mods-database **无 LICENSE**（默认 All rights reserved）：不能 fork/引代码，只能学方案；数据做种子需先取得作者授权。
- **XMCL 的发现机制是客户端遥测**：客户端解析本地 mod 文件、按文件 sha1 关联双平台（实测 23.4 万文件条目、双平台关联率仅 25.5%）——关联不是主流，单平台收录必须支持。
- **mcim-translate**（mcmod-info-mirror）用 LLM 全量翻译 description/summary，公开 API 可查——是现成的"描述翻译"参考实现，但名称翻译不覆盖、后处理粗糙。
- **中英混搜的命门是别名表**（社区译名↔英文名映射），不是翻译质量；mcmod 词典、XMCL 社区 CSV、CFPA 词典、用户反馈都是别名增量来源。
- **国内分发**：GitHub Release 直链对中文用户不可靠，需镜像（jsDelivr/ghproxy 或自建）。
- 遥测涉及隐私（搜索词、project id、文件 hash），需可关闭、匿名化。
