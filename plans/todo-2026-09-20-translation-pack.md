# 汉化包与端侧自动翻译

## 背景

- 启动器希望具备「游戏汉化包」能力：外挂汉化包以资源包形式加载进游戏、替换语言键，经 Trident 机制挂入实例资源包目录，源文件由 Polymerium 在外部管理。来源分两类：分发（直接用别人做好的汉化包）与自制（本地目录链入）——**自制是重点**。
- 自制的主要摩擦是翻译工作量。不想引入云端大模型：要求用户配置 API key、产生按量费用，对用户配置、开发适配和服务采购都是不现实的门槛。
- 已完成的头脑风暴与外部调研见 `ref-2026-09-20-ondevice-translation-models.md`（数字有时效，实施时重新核实）。

## 做什么

1. 汉化包管理：分发与自制两种来源的汉化包（资源包）外部管理，经 Trident 部署机制挂入实例；自制支持目录方式链入。
2. 端侧自动翻译：**先做 spike 验证**——取真实 mod 的语言文件（含占位符与格式代码的条目），对比端侧小 LLM 与 NMT 的产出质量，人工评估后再决定是否建完整翻译服务层。

## 想要什么效果

- 用户零配置（无 API key）、离线可用的一键自动翻译，产出草稿。
- 机器产出仅限个人使用，永不进入分发通道；分发级汉化包必须经人工或外部大模型制作。
- 术语表可作为独立资产分享，与分发生态咬合（别人可借他人术语表起步自动翻译）。

## 调研所得的注意事项

- **路线选择的关键分野**：NMT（opus-mt / bergamot）无 prompt 概念、逐句无状态，吃不进键名上下文与术语表；「根据上下文翻译」只有端侧小 LLM（Qwen3 1.7B/4B 量级）能满足，且 LLamaSharp 集成路径反而比 ONNX NMT 更短（现成 NuGet 含全平台后端）。NMT 仅作为轻量降级备选。
- **许可证红线**：NLLB 系列 CC-BY-NC 不可内置；Qwen3 与 OPUS-MT（Apache-2.0）、bergamot 模型（MPL-2.0）可再分发。
- **模型不打进安装包**：按需下载，模型存应用私有目录，国内走 hf-mirror。
- **真正决定可用性的是管线而非模型**：占位符与 § 格式代码保护、术语表、翻译记忆（增量更新时只翻新增键、保证全文件译法一致）、机器输出始终标记草稿。
- MC 生态现有自动翻译工具全部走在线接口，端侧无先例——是差异化机会，也意味着无现成轮子可抄。
