## 必须保留的目的

1. 整合包源（`import/`）保存整合包提供或作者维护的文件，跨实例重置保留。游戏对运行内容的修改不能自动写回 import；否则重置无法恢复源版本。作者仍可通过工作区主动把选定修改同步到 import。
2. 本地保留（`persist/`）承载用户优先级更高的内容，跨实例重置保留，而且可写。既包括单个配置文件，也包括 `saves/`、`screenshots/` 等会产生新文件的整个目录。
3. 运行目录（`build/`）是游戏使用的目录。重置清除其中未受保护的运行状态；其中可能包含存档、截图和配置，不能将重置描述为无损清理。
4. 普通部署对 import 的已有工作副本只补缺失，内容修改仍由用户手动同步；源的新增与删除要能在部署时跟随。整合包更新与普通部署的语义不同，更新要刷新整合包工作副本。
5. 文件优先级、目录投影、包部署与运行时写入要有明确归属。目录型资源包应能完整读取音乐、贴图、模型和语言等内容。
6. Trident 核心承担行为，CLI 与桌面应用共享结果。桌面工作区、快照、重置、导入导出与核心采用一致的数据边界。
7. 部署代码应线性、可读、可维护；解释中的“先 A，再 B，然后 C”要能直接对应代码中的执行分区。可以在同一方法中按顺序组织并用 `#region` 标出分区，不要求机械拆成多个外部函数或模块。

`live/` 并非目的本身；V3 的额外限制和实现选择不构成 V2 的硬约束——V2 最终保持当前目录布局与投影方式。

## 问题背景与历史依据

当前将 import 直接复制到 build 的模型依赖仍然存在的源文件识别工作副本。作者删除源文件后，build 的旧实体副本失去来源标识，普通部署不能可靠清理。GitHub [#93](https://github.com/d3ara1n/Polymerium/issues/93) 对应此场景。

历史代码可作为行为依据，但不得直接回退或复制旧实现：

| 位置 | 提交 | 事实 |
| --- | --- | --- |
| Trident | `1e6e1f8` | 引入 import/live 分离 |
| Trident | `b54141a` | 增加 live 孤儿文件清理 |
| Trident | `a1fea6a` | 移除 live，改为 import 在 build 中的实体副本 |
| Polymerium | `da61be2b` | 工作区、快照展示和重置适配移除 live |

旧机制复制 import 到 live 时只补缺失并保留修改时间，再将 live 链接到 build；build 中被 Delete-Create 写入替换成普通文件的目标会回迁到 live，再恢复链接。目录链接位置被普通目录占用时也有逐项回迁逻辑。旧更新清空 import/live，旧重置清空 build/live/锁文件，旧快照包含 import/live/persist，导出以 import 为文件源。

移除 live 的直接动机是目录型资源包的内部文件链接不能被游戏完整枚举。[#75 的讨论](https://github.com/d3ara1n/Polymerium/issues/75#issuecomment-4981897601) 区分资源包入口链接与包内文件链接。允许链接目标并不等于资源枚举会跟随内部链接；整个资源包目录链接具有可行依据，但仍需实际运行验收。

当前代码已重构：`SymlinkPhotos` 类不再存在，链接对账、回迁等职责由 `DeploymentPlanner` 规划、`SolidifyManifestStage` 执行。讨论中的“SymlinkPhoto 机制”指该职责，不要求恢复旧类。当前整合包更新已有暂存与回滚，不能退回直接删除目录的旧实现。

## V3 总体模型

```text
import ──┐
         ├─ 文件树仲裁，persist 优先 ──→ live 实体工作副本
persist ─┘                              ↕ persist 来源内容双向同步
                                         ↓
                          按合并后的 .keep 确定链接粒度
                                         ↓
package ───────────────────────→ 最终投影仲裁 ──→ build
                                         ↑
                        build 普通文件／目录回迁到 live
```

V3 的两个主要仲裁面：

- `{import ∪ persist} → live`：先决定源条目，再协调工作副本。persist 的优先级体现在源树合并上，其可写性体现在源与 live 的同步上。
- `{live ∪ package} → build`：合并最终投影意图，live 的冲突优先级高于 package。目录转发还决定其中其他文件链接的实际落点。

在 V3 基线中，persist 文件也实体化到 live。不要把后续提出的“persist 目录继续直接投影”混合方案当成已确认设计；它正是讨论尚未闭合的部分。

V3 希望用目录结构与链接表达归属，不引入记录历史文件来源的持久化清单。该选择带来的限制见后文；V2 最终引入了投影清单，未沿用该限制。

## V3 源文件树仲裁

### 文件级合并

import 和 persist 先以相对路径合并，persist 优先。此时 `.keep` 与其他文件一样参与合并，不因某层出现 `.keep` 就直接跳过另一层的整个目录。

例如：

```text
import/resourcepacks/A/.keep
import/resourcepacks/A/pack.mcmeta
import/resourcepacks/A/assets/example/a.ogg
persist/resourcepacks/A/assets/example/a.ogg
```

合并后的 live 中有 `.keep`、import 的 `pack.mcmeta` 和 persist 的 `a.ogg` 实体副本。随后将整个 live/resourcepacks/A 链接到 build。这个例子没有目录／文件链接冲突，也不要求把整个 A 接管到 persist。

文件与目录类型不能共存时仍须仲裁，例如 import 的 `a/b.txt` 与 persist 的普通文件 `a`。候选处理是高优先级条目遮蔽低优先级的冲突子树；具体类型切换、回迁和报错边界尚需实现前定稿，不能将不可共存条目同时交给应用阶段。

### 普通 import 工作副本

- 缺失则复制到 live，并保留源修改时间。
- 已存在则保留 live，普通部署不自动覆盖内容。
- 工作区提供主动同步到 import 和从 import 还原工作副本。
- 源被删除且 persist 没有接管时，清理对应工作副本和投影，但要遵守下文目录条目的清理边界。

### persist 与 live 双向同步

已接受采用修改时间决定同步方向，哈希用于判断内容是否相同，不用于猜测写入方向。

| 条件 | 行为 |
| --- | --- |
| live 文件缺失 | 从当前胜出的源复制 |
| persist 的 mtime 更新 | persist 覆盖 live |
| live 的 mtime 更新 | live 回迁到 persist |
| 两边时间、内容相同 | 无操作 |
| 两边时间相同但内容不同 | 按此前接受的裁决由 persist 胜出 |

同步保留胜出版本的修改时间；不能用同步发生时间制造新版本。内容相同而时间不同的元数据处理、时间精度及哈希执行策略属于实现细节，须保证重复部署收敛而非来回覆盖。

游戏删除 live 中的持久文件，不代表删除用户 persist 的意志：只要 persist 的源还在，下次部署重新补回。游戏不能通过删除工作副本来删除 persist 的源文件。

mtime 裁决不识别“新加入 persist”的事件。若 live 原来来自 import，而用户后来放入 persist 的 A′ 保留了更旧时间戳，live 的较新 A 仍可能回迁并覆盖 A′。本轮已选择按新旧裁决，不能又承诺“来源变化时 persist 无条件覆盖”。若需要后者，必须重新引入能证明上次来源的依据。

## V3 目录条目与 .keep

### 两个阶段的不同解释

- 源树合并时，`.keep` 是普通文件，可以记录它的胜出来源。
- 生成 live 到 build 的投影时，带 `.keep` 的目录成为整体链接的目录条目；其内部文件保持实体形态。
- 一个目录成为同步条目后，不能对其内部每个运行时新增文件套用“import/persist 没有同名路径就删除”的文件级孤儿规则。

目录条目内部豁免逐文件孤儿清理，是用户明确指出的边界。但它带来尚未解决的冲突：如果既要保留目录中新生成的文件，又要求删除 import 中某个源文件后自动删除对应旧副本，仅凭当前两棵目录树可能无法区分两者。该细节没有在讨论中完成设计，不能宣称已同时满足。

目录条目整体失去所有有效源及所有权时如何清理、`.keep` 增删时如何改变条目粒度，也需要统一处理。import 根、persist 根或 live 根是否允许通过 `.keep` 转发整个 build，尚未授权；当前核心对 persist 根整体投影有禁止约束，不能无意移除。

### persist 目录的新增内容与回迁

`persist/screenshots/.keep`、`persist/saves/.keep` 的目的包括保护目录未来产生的内容。新截图／新存档即使尚无 persist 同名文件，也应归入该持久目录，而不是当作无来源孤儿删除。

V3 曾讨论：根据目录条目的 `.keep` 胜出来源，如果由 persist 声明，则回迁整个目录中的运行时内容。该方案尚未闭合，尤其包括：

- 同一路径 `.keep` 同时存在于 import/persist 时由 persist 胜出。
- 嵌套 `.keep`、外层 import 目录与内部 persist 目录如何划分回写范围。
- 目录中由 import 提供的初始文件是否及何时成为 persist 文件。
- 用户在 persist 中删除文件，与 live 中较新副本之间如何协调。
- 整目录回迁必须识别系统生成的包链接，不能把缓存引用作为普通用户文件复制回源。

这个补充可以扩展保护范围，但不恢复原来的直接写入能力。游戏仍先写 live，再等待回迁，见“V3 局限”。

### 默认标记生成

已确认：整合包安装、导入、更新都要检查新 import 中实际存在的 `resourcepacks/{A,B,C}`，若是目录，则生成对应的 `{A,B,C}/.keep`。更新可在新 import 暂存阶段完成。

普通部署不重新生成标记。作者实例在新建或导入后由作者维护 import；本讨论中，作者自行维护的源没有后续软件驱动的整合包更新入口。作者后来增加 D 目录时，自行维护 D/.keep。

不要沿用原始计划中“更新时也不能重新生成默认规则”的要求；当前已明确允许在上述三个整合包接收过程重建 `.keep`。

新机制是否默认覆盖模组特有的其他资源路径，只能依据真实兼容验证扩展，不能从 resourcepacks 推断所有目录都适合整体链接。

## V3 最终投影与包仲裁

live 与 package 进入同一个最终投影阶段。package 的输出通常为文件，live 可以提供文件或带 `.keep` 的目录。

需要同时处理相同路径冲突、文件／目录类型冲突和父子路径关系。目录转发不等于无条件丢弃所有内部 package 候选：

```text
live/mods/.keep
package → mods/example.jar

结果可以是：
build/mods → live/mods
live/mods/example.jar → package cache
```

用户设置 mods/.keep 后，落在 mods 的包链接进入 live/mods 是已接受的行为。系统应保持状态一致，不能因这种用法少见就崩坏。

若 live 自身在同路径提供内容，则 live 优先。例如用户建立 `shaderpacks/Shader.zip/.keep`，该目录条目可以遮蔽 package 输出的同名 Shader.zip 文件；即便名称少见，也按统一规则处理。

投影层要解析目录转发后的实体落点。系统生成的 package 链接不能在下一次扫描中变成 live 用户源内容，也不能被持久回迁带入 persist；清理和重建必须与最终包候选一致。这一机制仍待具体设计，不能直接套用“源目录禁止一切符号链接”的当前扫描逻辑。

## V3 回迁、自愈与部署顺序

### 自愈职责

- 对于有效 live 投影路径，build 中已有普通文件时，按运行时写入接管并回迁到 live，保留 Delete-Create 修改，再恢复链接。
- build 中已有链接，无论当前指向 persist、旧 live 或其他被识别的托管目标，均由最终链接对账统一处理；不按历史版本散写迁移分支。
- 目录链接目标被普通目录占用时，复用并改造逐项回迁职责，识别其中的托管链接；不能递归跟随链接搬走其他层目标。
- 目录投影目标被普通文件占用等无法回迁的类型冲突应按明确错误处理，不能直接删除用户实体。

当前源码的承载位置已变化，需在当前规划／执行机制上实现这些行为；“历史机制已有”不代表当前代码可以不改就支持全部新布局。

### 执行次序与组织要求

依赖关系必须是：读取源与投影意图 → 接回 build 实体写入 → 协调 live/源 → 生成最终包与 live 投影 → 应用链接。具体阶段可以在现有方法内按分区组织，也可在有明确职责收益时拆分。

不能先用旧 live 的时间／哈希决定 persist 同步，再执行 build 回迁；否则刚接回的运行时修改要等下一次部署才能保留。应针对接回后的有效内容判断方向。也可通过一份能表达操作后状态的计划实现依赖，但不能让只读规划阶段暗中写文件。

代码可视性要求的是顺序与职责清楚，不要求固定方法数量、类名或恢复旧 stage。链接应用不应散落业务回调，让它在遍历时临时决定 persist 同步策略。

## V3 生命周期与外部边界

### 重置

先接回 build 中的运行时写入并完成持久内容同步，再清理 build、live 和部署锁；保留 import、persist，以及现有契约要求保留的其他用户数据。回迁失败不能继续删除唯一有效副本。

这只能保存已归入持久范围的内容。其他运行数据会被重置永久删除，不能称作无损恢复。

### 整合包更新

1. 准备并验证新 import、默认 `.keep`、附件和原生 Patch 导入层。
2. 仍按更新前的源归属接回运行时写入，完成持久内容同步。
3. 将旧 import、旧工作副本、需替换的投影和新 profile 纳入现有暂存／提交／回滚流程。
4. 更新成功刷新整合包工作副本；下一次部署从新 import 与 persist 重建。更新失败恢复旧源、工作副本及所需投影。

persist 中的玩家修改不能因失败回滚丢失；Patch 用户层及现有附件处理也不能因恢复旧模型而退化。上述是必要顺序和结果约束，事务实现尚未完成设计。

### 快照、工作区与导入导出

- 工作区继续面向整合包源与工作副本，提供显式同步到 import 和还原。live 混入 persist 后，哪些条目属于工作区展示范围、如何显示被 persist 覆盖的 import 文件，需要补充设计。
- 新快照需一致捕获 profile、源、工作副本、持久数据及现有 Patch 范围；live/persist 同一内容重复保存、恢复时同步方向等问题尚待定稿。
- 现有快照可能使用 build/ 前缀表示工作副本，历史快照还可能使用 live/；新机制不能仅因物理目录调整而将旧快照引用错误恢复到运行投影中。恢复适配是明确待办，不属于普通链接自愈。
- 整合包导出继续以 import 为可分发文件源。live/persist 的游戏修改只有经作者显式同步到 import 才进入整合包。
- `.keep` 是实体标记，原生及外部格式的导出、重新导入和默认生成行为需要一致验证；不应再凭空设计一套尚未采用的源规则序列化格式。

## 存量上线目标与可证明范围

目标是普通部署可自动接管现有实例，无需用户手工重置或搬目录；采用常规回迁和链接对账，而非按版本分叉。

这个目标不等于完全没有转换或兼容代码，也不能追回已经丢失的来源事实：

- 仍有 import/persist 对应路径的 build 普通文件，可以由常规回迁接管。
- 已有托管链接的目标切换可以由链接对账处理。
- 升级前已删除源文件、仅剩 build 普通文件的旧孤儿，无法仅凭当前源树区分于用户自建文件；不能保证自动清理。
- `.keep` 目录接管、未知链接、文件／目录类型变化和中断后重试需要实际验证。
- 旧快照恢复有独立的格式／路径兼容问题，不能归入链接对账后宣称无需处理。

## V3 的已知局限与尚未闭合处

| 问题 | 影响／当前状态 |
| --- | --- |
| persist 全量实体化到 live | 增加复制、扫描和磁盘占用，尤其是大型存档目录 |
| 持久内容延迟回迁 | persist 不再是游戏直接写入位置；崩溃、直接删除 live 或跳过协调入口可能留下较旧的持久副本 |
| `.keep` 原始目的弱化 | 原来可减少复制并让整目录直接写入；V3 主要保留了链接粒度与资源读取价值 |
| mtime 无法识别来源变更 | 新加入 persist 的旧时间戳文件可能被 live 覆盖，这是统一按新旧裁决的代价 |
| 目录豁免与源删除跟随 | 新增运行文件和已删除源的旧副本可能表现为同一状态，完整删除语义尚未解决 |
| persist 目录整体回迁 | 胜出 `.keep` 的来源、嵌套归属与新增文件保护仍需明确；不能只靠现存 persist 文件路径判断 |
| package 链接进入 live | 需要识别派生链接，避免它们进入源仲裁、被回迁或错误清理 |
| 回迁后状态参与规划 | 现有先计划后执行的流程需要表达依赖，不能使用失效的时间／内容判断 |
| 生命周期范围扩大 | update/reset/snapshot 必须理解持久副本同步；原来的直接写入不需要这些额外保障 |
| 资源包兼容范围 | 目录入口链接的可行性不等于所有 Minecraft 版本和模组资源路径都已验证 |
| 上线和快照兼容 | 普通自愈覆盖可识别条目，不覆盖未知旧孤儿和所有历史快照语义 |

### 已排除的误解

- `import/A/.keep` 加 `persist/A/file` 在纯 V3 中可以合并为 live 的实体目录；不存在必须报错或整目录转移到 persist 的冲突。
- “persist 普通文件必须始终直接写入 persist”不是 V3 的要求；已接受普通文件经 live 按 mtime 同步。
- “persist 的 `.keep` 目录应恢复直接写入”是用于评估 V3 价值的目标，尚未形成与纯 V3 混合后的完整设计。
- import 整目录投影与内部 persist 整目录直接投影的嵌套冲突，属于上述混合方案的问题，不能拿来否定纯 V3 示例。
- 目录条目不等于所有内部 package 输出都被遮蔽，也不等于所有内部运行时新增文件都是孤儿。
- `.keep` 生成时机为安装／导入／更新；不是每次部署，也不是作者后续维护源时的软件自动行为。

## 与原始 UI 计划的关系

保留现有包部署规则能力。原始计划还提出改善规则浏览、创建、编辑、启用禁用和删除体验；这一诉求尚未实施。

由于 V3 探索复用 `.keep`，原定顶部切换“包／整合包源”的双规则编辑器及默认源规则体系不能再当作既定 UI。是否继续做包规则 UX、是否增加 `.keep` 的可视化管理，应在核心语义选择后单独确定，不从本次机制讨论推导额外已授权实现。

## 验收要求

采用某个方案并实施后，用真实整合包和实际游戏运行确认：

- 源新增、内容手动同步、源文件与目录删除、工作副本还原。
- persist 单文件新旧裁决、删除后补回、持久目录中新存档／新截图。
- 游戏正常覆盖与 Delete-Create 写入，以及接回后同次操作完成持久同步。
- 资源包目录中的音频、贴图、模型、语言读取。
- 文件级／目录级投影切换、跨层覆盖、mods/.keep 下包投影、文件／目录冲突。
- 更新成功、失败和取消，重置前回迁，快照及旧快照还原。
- 现有实例首次部署、重复部署、无关 build 内容和 persist 数据保护。
- CLI 与桌面入口的一致性、导出文件边界。

构建只验证编译；遵守仓库不新增功能测试项目、不运行格式化工具的约定。
